# 잘 쓰는 법 (본문 + description)

## description이 스킬의 운명을 정한다

Claude는 스킬 목록에서 **name + description만** 보고 "이 스킬을 쓸까?"를 판단합니다. 그래서
description이 부실하면 스킬이 안 켜져요(초보자 실패 1위). description에는 두 가지를 넣습니다:

1. **무엇을 하는가** — 이 스킬의 기능.
2. **언제 켜지는가** — 실제 사용자가 할 법한 말·상황을 **구체적으로**.

### 나쁜 예 vs 좋은 예

```
나쁨:  description: 데이터를 정리하는 스킬.
```
→ 너무 막연해서 언제 켜야 할지 Claude가 모릅니다.

```
좋음:  description: >-
  엑셀/CSV의 지저분한 표를 정리하고 계산 컬럼을 추가하는 스킬. "다운로드 폴더의 xlsx 정리해줘",
  "매출 표에 이익률 컬럼 추가", "이 csv 열 좀 맞춰줘" 같은 요청에서 켜진다. 사용자가 파일명을
  대충 말하거나 '스프레드시트'라고만 해도 적용한다.
```
→ 기능 + 구체적 트리거 문구 + 애매한 표현까지 커버.

### 팁: 조금 "밀어붙이듯" 써라

Claude는 스킬을 **과소 사용(안 켜는)** 경향이 있습니다. 그래서 "~할 때 **반드시** 사용",
"사용자가 정확히 그 단어를 안 써도 ~면 적용" 같은 표현을 넣어 트리거를 강하게 잡아주세요.
단, 관련 없는 상황까지 켜지게 하면 안 되니 **범위는 명확히** 합니다.

### 트리거 자가 점검 (should-trigger / should-not-trigger)

description을 쓴 뒤, 스스로 테스트 문장을 만들어 보세요:
- **켜져야 하는 문장** 5개 — 다양한 말투(격식/반말/오타 포함), 스킬 이름을 직접 안 쓴 것도.
- **켜지면 안 되는 문장** 5개 — 특히 **비슷해 보이지만 다른** 요청(키워드는 겹치는데 실제론
  다른 도구가 맞는 경우). 이런 "낚시" 케이스를 통과해야 좋은 description입니다.

## 본문 쓰는 원칙

### 1) 명령형으로 써라
"~하면 좋습니다"보다 **"~하라"**. Claude에게 주는 지침이니 동작을 분명히.

### 2) "왜"를 함께 써라 (가장 중요)
딱딱한 "무조건 ~하라(ALWAYS/NEVER)"를 남발하지 마세요. 요즘 모델은 똑똑해서 **이유를 알면**
규칙을 더 잘 지키고 새로운 상황에도 응용합니다.

```
약함:  포트레이트는 반드시 25~30%로 해라.
강함:  포트레이트는 시트의 25~30%로 둬라 — Seedance가 얼굴을 오직 이 부분에서 읽기
       때문에, 작으면 정보가 부족해 매 샷 얼굴이 달라진다.
```

### 3) 출력 형식을 정할 땐 템플릿을 보여줘라

```markdown
## 보고서 형식
항상 이 틀을 써라:
# [제목]
## 요약
## 핵심 발견
## 권고
```

### 4) 예시를 넣어라 (입력 → 출력)

```markdown
## 커밋 메시지 형식
예시 1:
입력: JWT 토큰으로 사용자 인증 추가함
출력: feat(auth): implement JWT-based authentication
```

### 5) 좁은 예시에 과적합하지 마라
스킬은 **수천 번, 다양한 요청에** 쓰입니다. 특정 예시에만 맞는 세세한 규칙을 박으면 다른
상황에서 깨집니다. 원리를 설명해 일반화되게 하세요.

## 안전 원칙 (반드시 지킬 것)
스킬에는 악성코드·해킹·데이터 탈취 등을 돕는 내용을 넣지 않습니다. 스킬의 의도는 이름만 봐도
투명해야 합니다("XYZ인 척 롤플레이" 정도는 괜찮습니다).
