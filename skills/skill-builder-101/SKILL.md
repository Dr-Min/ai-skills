# 스킬 만들기 101 (초보자용)

이 스킬은 **처음 스킬을 만드는 사람**을 위한 안내서입니다. 어려운 용어는 그때그때 풀어서
설명하고, 실제로 동작하는 스킬 하나를 끝까지 만들어 설치하는 것까지 데려갑니다.

## 스킬이 대체 뭔가요? (한 문장)

**스킬 = Claude가 특정 상황에서 자동으로 펼쳐 읽는 "미리 써둔 매뉴얼"** 입니다.

평소 Claude는 매번 즉흥적으로 판단하지만, 스킬이 있으면 관련 작업이 들어왔을 때 그 매뉴얼을
열어 **매번 같은 기준·순서로** 일합니다. 예를 들어 "계약서 검토" 스킬이 있으면, 당신이 계약서
얘기를 꺼낼 때마다 Claude가 그 스킬을 열어 정해진 체크리스트대로 검토해요.

핵심은 이거예요:
- 스킬은 **AI를 훈련(training)시키는 게 아닙니다.** 그냥 텍스트 지침 묶음이에요.
- Claude가 **알아서 적절한 순간에** 불러옵니다(그 판단은 `description`이 좌우 — 아래 참고).
- 그래서 잘 만든 스킬 하나면, 같은 품질의 결과를 **몇 번이고 재현**할 수 있습니다.

## 스킬은 어떻게 생겼나요? (구조)

가장 단순한 스킬은 **폴더 하나 + 그 안의 `SKILL.md` 파일 하나**면 끝입니다.

```
my-skill/                 ← 스킬 폴더 (이름 = 스킬 이름, 영어 소문자-하이픈)
├── SKILL.md              ← (필수) 지침의 본체
└── references/           ← (선택) 길어지는 내용을 따로 뺀 참고파일들
    ├── details.md
    └── examples.md
```

`SKILL.md`는 두 부분으로 되어 있습니다:
1. **Frontmatter** — 맨 위 `---` 사이의 설정(이름·설명). **필수.**
2. **본문** — 실제 지침(마크다운으로 자유롭게).

```markdown
---
name: my-skill
description: 이 스킬이 무엇을 하고 언제 켜져야 하는지 한두 문장. (트리거의 핵심)
---

# 제목

여기에 Claude가 따라야 할 지침을 씁니다.
```

## 스킬 만드는 5단계 (이 순서대로 도와주세요)

초보자가 스킬을 만들 때는 아래 순서로 함께 진행합니다. 각 단계의 자세한 방법은 해당 참고파일을
열어 그 기준대로 안내하세요.

1. **무엇을·언제 (의도 잡기)** — "이 스킬이 뭘 해줬으면 하나요? 어떤 말을 했을 때 켜지길
   원하나요? 결과물은 어떤 형태(문서·표·체크리스트)인가요?"를 먼저 물어 명확히 합니다.
2. **구조 정하기** — 내용이 짧으면 `SKILL.md` 하나로, 길거나 주제가 여럿이면 `references/`로
   나눕니다. → `references/anatomy.md`
3. **본문·description 쓰기** — 지침을 명령형으로 쓰고, **description에 "언제 켜지는지"를 구체적
   으로** 넣습니다(트리거의 90%가 여기서 결정). → `references/writing-guide.md`
4. **(필요시) MCP 도구 연동** — 슬랙·구글드라이브·법령검색 같은 외부 도구를 쓰는 스킬이면 MCP를
   연결합니다. → `references/mcp-integration.md`
5. **패키징·설치·배포** — `.skill` 파일로 묶어 설치하고, 원하면 git/플러그인으로 공유합니다.
   → `references/packaging.md`

막히면 `references/examples.md`에 통째로 베낄 수 있는 완성 예시가 있습니다.

## 초보자가 가장 자주 틀리는 3가지 (먼저 알려주세요)

1. **description을 대충 씀** → 스킬이 안 켜집니다. "언제 써야 하는지"를 실제 사용자가 할 법한
   말과 함께 구체적으로 적어야 해요. (강의 팁: 오히려 조금 "밀어붙이듯" 써라 — Claude는 스킬을
   과소 사용하는 경향이 있어서.)
2. **SKILL.md에 모든 걸 다 욱여넣음** → 너무 길면 비효율. 500줄 넘어가면 `references/`로 쪼개고
   본문에는 "언제 무엇을 읽어라"만 남기세요(progressive disclosure).
3. **"이렇게 해라"만 쓰고 "왜"를 안 씀** → 요즘 모델은 똑똑해서, 이유를 알려주면 규칙을 더 잘
   따르고 응용도 합니다. 딱딱한 "무조건 ~하라"보다 "~하면 ~가 깨지니 ~하라"가 낫습니다.

## 이 가이드를 쓰는 법 (Claude에게)

사용자가 스킬을 만들고 싶어 하면:
- 먼저 위 **1단계(의도 잡기)** 질문을 던져 무엇을·언제·어떤 결과물인지 확정합니다.
- 그다음 필요한 참고파일을 열어 그 기준대로 실제 파일을 만들어 줍니다(사용자 대신 작성).
- MCP가 필요한지 반드시 확인하고, 필요하면 `mcp-integration.md`를 적용합니다.
- 마지막에 `packaging.md`대로 `.skill`로 묶어 설치·공유까지 안내합니다.
- 절대 사용자에게 "알아서 해보세요"라고 떠넘기지 말고, 초보자가 따라올 수 있게 손을 잡고 갑니다.
